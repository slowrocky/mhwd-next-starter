## Sanity TypeGen

The standalone Studio and frontend must be sibling folders:

```text
MHWD/
  mhwd-next-starter/
  mhwd-next-starter-studio/
```

From `mhwd-next-starter-studio`, run `npm run typegen` after changing the
product schema or queries in `src/sanity/lib/queries.ts`. Studio development
also runs schema extraction and TypeGen automatically. Studio builds extract
the schema, then the `postbuild` script regenerates types. Restart an
already running Studio once after changing `sanity.cli.ts`.

Types are generated into `src/sanity/types.ts`. Do not edit this file manually;
include its changes in the frontend commit alongside query changes. The
intermediate `schema.json` is ignored in the Studio repository.

`client.fetch()` infers results from named `defineQuery` queries without manual
generic types. Required schema fields are generated as required: this assumes
published, validated content. Revisit that assumption when adding draft previews.

The frontend can lint and build using the generated types without running Studio.
If the sibling folders are renamed, update the paths in the Studio's
`sanity.cli.ts`. Keep queries in the configured file or extend its `typegen.path`.

## Published content updates

Homepage and product detail fetches share `sanityFetchOptions` in
`src/sanity/lib/client.ts`: Next.js caches published Sanity content with a
60-second revalidation interval. `useCdn: false` avoids a second data cache
when refreshing. Images still use Sanity's image CDN and `next/image`.

This is request-driven stale-while-revalidate, not a scheduled refresh or a
guarantee that a publication appears within exactly 60 seconds. The first
request after expiry can receive stale content while Next.js refreshes it in
the background. A subsequent request receives the updated content. If Sanity
is temporarily unavailable, the last successful cached response can remain.
An already open page does not update itself; reload or revisit it.

No token or webhook is needed for the public dataset. The unused `live.ts`
scaffold is not part of this setup. Instant updates and draft previews are
separate future features.

Verify caching with `npm run build` followed by `npm run start`; development
mode and hot reload do not reproduce production cache behavior. To check a
publication end-to-end, change and publish a test product in Studio, wait for
the interval to expire, and revisit both pages (then revisit after the
background refresh). No new build should be needed.

## Product SEO

Product metadata uses the published name, description and image, with the site
description as fallback. Metadata and page rendering share a request-memoized
product fetch. Missing/inactive products use `notFound()` (including `noindex`).

The sitemap lists the homepage and published active products with nonempty
slugs. Product `lastModified` comes from Sanity's `_updatedAt`; the static
homepage does not claim a new modification date on every generation. Sitemap
data uses the same 60-second revalidation policy as product pages.

Before deploying a client site, set `siteConfig.url` to its real public origin.
Canonical URLs, Open Graph URLs, robots and sitemap currently use the starter
placeholder `https://example.com`.

## Site settings

The standalone Studio has one `Nastavenia webu` singleton for the site name,
short name, description, public URL, locale, contact details, navigation and
social links. Its fixed document ID is `siteSettings`; the Studio structure
keeps it out of regular document lists.

Until that document is published, the frontend uses the starter defaults in
`src/config/site.ts`. This makes the initial setup safe and lets a fresh clone
build before a client fills in CMS content. After publishing settings, the
header, footer, root metadata, product metadata, robots and sitemap use CMS
values with the same 60-second revalidation policy.

For a new client, open `Nastavenia webu` in Studio, complete all four sections
and publish it. Set the real public URL before deployment: it supplies canonical
URLs, Open Graph URLs, `robots.txt` and `sitemap.xml`.

## Services

`/sluzby` lists published services with status `Aktívna`. The service model has
a name, slug, short description and optional image; `Skrytá` services remain in
Studio but are not sent to the website. Each card links to `/sluzby/[slug]`.
Details have their own canonical URL, share metadata and appear in the sitemap.
